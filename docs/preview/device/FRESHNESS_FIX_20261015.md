# 固定確認版：鮮度の分離と初期表示テスト

## なぜ必要か／現状不足か／最小安全か

- 保存時のPASS・警告0件と、相談時点の鮮度を区別する必要がある。
- 既存の相談文には鮮度評価がなく、配信照合日時も株価更新と誤読され得た。UIテストでは初期描画前の時計固定が保証されず、同じ条件で結果が変わった。
- device確認版の相談文・日時説明とテストに限定する。固定配信4ファイル、指標、Core、通常UI・SW、投資条件、個人記録、s1本体・PINSは変更しない。

## 原因を観測した証拠

修正前の観測commit `63b9117acc94db11c3fef0f9bf5160865ece0eea`、UI Preview Verification run `38586522846`。

- srcdoc内の最初のスクリプト: `2026-10-14T15:07:46.347Z`（実日時）。
- 後から読むDate: `2026-10-04T09:30:00.000Z`（固定日時）。
- 後から評価したモデル: `age=2`, `reasons=[]`。
- 初期DOM: 4暦日超の警告が残存。

したがって、テストのcontext.add_init_scriptによる時計の差し替えが、このsandbox/srcdocでは初期実行に間に合わなかった。アプリの鮮度条件を解除して解決しない。

テスト専用HTTPサーバーが生成srcdocの同じscriptの先頭に時計設定を置く。PINS対象ファイルはそのまま読み込み、画面のモデル・起動・描画関数は変更しない。新規コンテキストで新しい日付の起動を反復し、JSTで4暦日目から5暦日目に変わる境界の初回表示も検査する。強制再描画・待機延長によって警告を隠さない。

## 検証対象

- Node: 保存時品質保持、12暦日前のSTALE、JST日付境界、無効/未来日、無効時計、照合日時だけ更新しても鮮度不変、要点/全文/分割一致、ハッシュ整合。
- UIブラウザ: 初回時計、繰り返し初回起動、4→5暦日の初期警告、既存の画面・コピー・250本表示・通常記録保持。
- deviceブラウザ: 日時の説明、要点/全文の評価日時一致、保存文一致、オフライン再起動・復帰と通常PWAの分離。
- 自動検証はiPhone/Safariでの正式受入ではない。

実行結果はPR #39のCIおよび公開後コメントに記録する。通常PWA採用・Production昇格は対象外。
